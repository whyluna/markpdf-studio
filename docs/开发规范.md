## 1. 技术栈（冻结选型，变更需评审）

| 层 | 技术 | 说明 |
|---|---|---|
| 语言 | Swift 5.9+ | 严格并发检查逐步开启（`SWIFT_STRICT_CONCURRENCY = minimal`） |
| UI | SwiftUI 为主 + AppKit 嵌入（`NSViewRepresentable`） | 文件树、标签栏用 AppKit 级精细控制时可下沉 |
| PDF | PDFKit | 标注读写全部走标准 PDF Annotation |
| MD 编辑器 | WKWebView + CodeMirror 6（本地打包，无 CDN） | 渲染插件：KaTeX、highlight.js、mermaid 均本地化 |
| 构建 | Xcode 15+，SwiftPM 管理依赖 | 不引入 CocoaPods/Carthage |
| 目标系统 | macOS 13.0+ | Apple Silicon / Intel 双架构 |
| 依赖白名单 | 原生侧**默认零第三方依赖**；新增依赖必须在 PR 中说明理由 | Web 侧依赖锁定版本并入库 |

## 2. 项目结构

```
MarkPDF/
├── MarkPDF.xcodeproj
├── MarkPDF/
│   ├── App/                        # 入口、AppDelegate、应用级状态
│   ├── Features/
│   │   ├── Workspace/              # 文件树、标签页、分栏、工作区状态
│   │   ├── MarkdownEditor/         # SwiftUI 包装层（MarkdownEditorView）
│   │   ├── PDFReader/              # 阅读视图、目录、缩略图、搜索
│   │   ├── PDFAnnotation/          # 标注工具、列表面板、写回/sidecar 存储
│   │   ├── Search/                 # 文件名模糊搜索、全文搜索
│   │   └── Settings/
│   ├── Core/
│   │   ├── Models/                 # DocumentModel、AnnotationModel（纯值类型）
│   │   ├── Services/               # FileWatcher、AnnotationStore、ExportService
│   │   └── Bridge/                 # WebBridge：WKWebView 消息协议层（唯一通道）
│   ├── Resources/
│   │   ├── Web/                    # ★ MD 编辑器内核：纯 HTML/JS/CSS，
│   │   │                           #   可在任意浏览器独立运行与调试
│   │   └── Themes/                 # 明暗主题 CSS + NSColor 资产
│   └── Assets.xcassets
├── MarkPDFTests/                   # 单元测试
├── MarkPDFUITests/                 # UI 冒烟测试
└── .github/workflows/macos.yml     # CI：macOS runner 编译 + 测试
```

约定：
- `Features/*` 只依赖 `Core/*`，禁止 Feature 之间互相 import
- `Core/Models` 为纯值类型（struct），不含任何 UIKit/AppKit/SwiftUI import
- `Resources/Web` 下的编辑器内核**禁止**依赖 WKWebView 专有 API 才能完成基础编辑——必须保证在普通浏览器里可运行、可调试（这是沙箱调试策略的前提）

## 3. 架构规范

### 3.1 总体模式
- SwiftUI 视图 + **MV（Model-View）+ 单向数据流**：状态对象（`@Observable` 类）持有状态并暴露意图方法（intent），视图只读状态、只调意图，不直接改数据
- 不引入 TCA/RxSwift 等重型框架

### 3.2 状态与所有权
- 每个 Feature 一个 `XxxStore` 状态对象，生命周期归 Scene 级容器持有
- `Core/Services` 为协议化单例（`protocol XxxService` + `final class LiveXxxService`），测试时用 mock 替换

### 3.3 线程规则
- 主线程只做 UI；文件 IO、PDF 文本提取、全文搜索一律 `async` 挂到后台
- 跨线程数据只允许值类型传递；`@MainActor` 标注所有 Store

### 3.4 WebView 桥接协议（唯一通道，禁止散点调用）
Swift 与 Web 内核之间只允许通过 `WebBridge` 收发**类型化 JSON 信封**：

```json
{ "id": "req-uuid", "type": "editor.setContent", "payload": { "text": "..." } }
```

- 消息类型集中于 `Bridge/MessageType.swift` 枚举定义，新增消息类型必须同时登记 TS 侧类型
- 请求-响应模式：带 `id` 的消息必须收到对应 `id` 的回应，超时 3s 报错
- Web 侧统一入口 `window.bridge.post(envelope)`，禁止页面内任意位置直接调 `webkit.messageHandlers`

## 4. 代码风格

1. 遵循 [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/) 与 `swift-format`（配置入库，提交前自动跑）
2. 缩进 2 空格；行宽 120；大括号 K&R 风格
3. 命名：类型用大驼峰，成员用小驼峰；布尔读作断言（`isLoading`、`hasAnnotations`）；异步函数动词开头（`loadAnnotations()`）
4. 访问控制：默认 `internal`；跨模块暴露才用 `public` 并附文档注释；禁止滥用 `open`
5. 文件组织：一个文件一个主类型；扩展分块用 `// MARK: -` 分隔；`// TODO(名字):`、`// FIXME(名字):` 必须带责任人
6. 禁止 `print` 提交入库（用日志，见 §6）；禁止强制解包，除非附注释说明不变式
7. SwiftUI 视图 body 超过 60 行必须拆子视图；预览宏 `#Preview` 必备（能预览的视图都要可预览）

## 5. Git 规范

- 分支：`main` 直推（经决策采用方式 A），CI 绿为健康线
- Commit message 采用 Conventional Commits：
  `feat(pdf): 支持下划线标注写回` / `fix(editor): 修复表格内光标丢失` / `chore(ci): 升级 macos-14 runner`
  类型：`feat | fix | docs | refactor | test | chore | perf`
- 提交自审清单：
  - [ ] 对应需求编号（FR-x.x）已标注
  - [ ] swift-format 通过、无新增警告
  - [ ] 新增逻辑有单测；UI 变更附截图/录屏
  - [ ] 与 HTML 设计稿不一致处已说明原因
- 禁止 `git push --force` 到 main

## 6. 日志与调试规范

```swift
import os
extension Logger {
  static let pdf = Logger(subsystem: "com.whyluna.markpdf", category: "pdf")
  static let editor = Logger(subsystem: "com.whyluna.markpdf", category: "editor")
  static let workspace = Logger(subsystem: "com.whyluna.markpdf", category: "workspace")
}
```

- 级别约定：`debug`（流程细节）/ `info`（关键动作，如文件打开）/ `notice`（降级与重试）/ `error`（用户可感知的失败）/ `fault`（数据损坏风险）
- 日志不含用户文档内容正文，只记路径哈希与长度（隐私）
- Release 编译剥离 `debug`；排查真机问题时引导用户从「控制台.app」过滤 `com.whyluna.markpdf` 导出

## 7. 测试规范

| 层 | 范围 | 要求 |
|---|---|---|
| 单元测试（XCTest） | Core/Models、Core/Services、标注写回、导出格式化 | 核心模型覆盖率 ≥ 70%；每个 bugfix 必须附回归测试 |
| Web 内核测试 | Resources/Web 下编辑器逻辑 | vitest + 浏览器环境；内核 CI 中 `npm test` |
| UI 冒烟（XCUITest） | 启动、打开工作区、打开 md/pdf、切换标签、分栏 | 5 条关键路径，CI 可跑 |
| 手动验收 | 每项需求按 PRD 验收标准逐条过 | 真机执行，结果记录于 PR |

## 8. 协作、验证与 Debug 流程（重要）

> 背景：开发产出方运行在 **Linux 沙箱**（无 Xcode/macOS SDK/图形界面），无法直接编译运行 macOS 应用。为保证质量，约定以下四层验证流程，每层有明确的输入、出口标准与责任人操作。

### 8.1 四层验证体系

| 层 | 验证对象 | 环境 | 出口标准 |
|---|---|---|---|
| ① HTML 原型 | 界面布局、交互、视觉 | 沙箱 Chromium | 与你确认后再进入 SwiftUI 实现；SwiftUI 实现以原型为基准逐像素对齐 |
| ② Web 内核 | MD 编辑器（本项目技术风险最高项） | 沙箱 Chromium + vitest | 内核在浏览器内通过全部编辑交互测试后，才允许嵌入 WKWebView |
| ③ CI 编译 | Swift 代码编译、单元/UI 测试 | GitHub Actions `macos-14` runner，执行 `xcodebuild -scheme MarkPDF build test` | 每次 push 构建绿；构建日志作为缺陷定位依据 |
| ④ 真机确认 | 真实体验、性能、PDFKit 行为 | **你的 Mac**（Xcode） | 按 PRD 验收标准逐条通过 |

### 8.2 真机反馈标准动作（用户侧）
1. **编译错误**：Xcode Issue Navigator 整段复制（含文件、行号、错误描述）贴回
2. **运行异常**：「控制台.app」过滤 `com.whyluna.markpdf` → 导出日志 + 录屏/截图
3. **崩溃**：`~/Library/Logs/DiagnosticReports/` 下对应 `.ips` 崩溃报告发回
4. 反馈粒度：一次一个问题，标注「操作步骤 → 期望 → 实际」

### 8.3 功能交付标准动作（开发侧）
每个功能交付时附带：
- 对应 PRD 需求编号与验收清单
- 真机自测步骤（编号化，可照做）
- 已知限制说明

### 8.4 迭代节奏
以周为迭代单位：周初确定本期需求子集 → 原型/内核先行确认 → 原生实现 → CI 绿 → 真机验收 → 周末复盘。

## 9. 性能规范

1. 主线程禁止文件 IO、PDF 文本提取、JSON 大解析
2. PDF 页面渲染：仅栅格化视口页 + 前后各 2 页；缓存上限 200MB，LRU 淘汰
3. 文件树：>5000 节点启用懒加载；FSEvents 回调防抖 300ms
4. 编辑器：单文档超 2MB 时降级为源码模式并提示（WYSIWYG 大文档性能为已知风险，见 PRD R1）
5. 每个里程碑用 Instruments（Time Profiler / Leaks / Energy）跑一次例行检查，报告归档

---

## 10. 安全与隐私规范

- App Sandbox 开启；entitlements 仅申请 `com.apple.security.files.user-selected.read-write`（及必要的下载目录访问），**不申请网络权限**
- 用户文档内容不出本机；日志不落正文（见 §6）
- 写回 PDF 前创建 `.bak` 一次性备份；任何写盘操作用原子写入（写临时文件后 rename）
